Lo último que explicó Cynthia fue sobre el sistema de logs y sus niveles, como respuesta a la pregunta de Claudio sobre cómo funciona el proceso completo. 1

¿Cómo funciona el sistema completo?

Al usuario le llega el mensaje genérico (por ejemplo, "Gracias por tu mensaje, un miembro de nuestro equipo te va a responder pronto") cuando ocurre un error. 2
Por dentro, el sistema guarda el log del error para que el equipo técnico pueda revisarlo posteriormente. 1
Niveles de log: 3

Info: Confirmación de que todo está funcionando bien.
Warning: Algo no está saliendo como debería, pero el programa todavía puede funcionar. 4
Error: Un problema serio que puede romper el programa. 5
Critical: Fallo total, el sistema no responde. 5
¿Por qué se usa Warning en lugar de Info?

Usar Info genera un log demasiado grande porque registra también los casos exitosos. 6
Con Warning, solo se registran los eventos relevantes: warnings, errores y críticos, evitando que el archivo de log crezca innecesariamente. 7
Objetivo final: El sistema tiene dos capas de protección: 8

El usuario recibe una respuesta amigable sin ver el error técnico. 9
El equipo técnico puede revisar el log para saber cuándo ocurrió el error, qué pasó y por qué.

Explicación del Callback Handler
El BaseCallbackHandler funciona como un listener (escucha) que monitorea diferentes eventos generados dentro de las cadenas de LangChain. 1

Eventos que puede capturar:
Cuando una cadena empieza o termina 2
Cuando se inicia o completa una petición al LLM 2
Cuando ocurre un error → evento on_chain_error 2
¿Cómo funciona?
Se crea una clase que hereda de BaseCallbackHandler, llamada "CapturaError" o similar. 2 Cuando ocurre un error en la cadena, en lugar de pasar directamente al fallback, el callback captura y registra el error primero en el error.log. 34

Comportamiento importante:
Si hay un error (por ejemplo, en la API Key), como el enrutamiento tiene varios pasos, el error se registra tantas veces como pasos tenga la cadena. 56 Esto permite ver exactamente qué tipo de error ocurrió (ej. error 401 de autenticación). 6

Alternativa más sencilla: exception_key
Sin necesidad de un callback completo, el fallback puede recibir un parámetro exception_key que envía un diccionario con el error correspondiente a la respuesta genérica. 7 Esto permite registrar el error específico de forma más simple. 8

¿Cuándo usar cada uno?
Callback Handler → cuando se necesitan más acciones ante un error (más flexible y potente). 8
exception_key → cuando solo se necesita registrar el error (más sencillo). 8



------------------------------




Cómo funciona exception_key
exception_key es una alternativa más sencilla al Callback Handler completo para capturar detalles específicos del error dentro de un fallback. 12

Mecanismo principal:
Cuando se activa el fallback, exception_key envía un diccionario que contiene el error específico a la función de respuesta genérica. 2
Se especifica un nombre de clave (por ejemplo, "error") y la excepción real se adjunta automáticamente a ella. 2
Dentro de tu función fallback (por ejemplo, fallback_con_log), puedes registrar ese error específico en tu error.log. 3
Flujo de ejemplo:
La cadena principal falla (ej. error de autenticación 401 en la API). 4
En lugar de solo registrar un mensaje genérico "cadena principal falló", exception_key pasa el detalle real de la excepción. 4
El logger registra el mensaje de error completo (ej. no autorizado, error 401). 4
¿Cuándo usarlo?
✅ Usa exception_key cuando solo necesitas registrar el error específico — requiere cambios mínimos en el código. 3
⚙️ Usa el Callback Handler cuando necesitas acciones adicionales más allá del registro (más potente pero más complejo). 3
Diferencia clave con el Callback Handler:
Callback Handler	exception_key
Momento	Captura el error antes del fallback 5	Pasa el error a través del fallback 2
Complejidad	Mayor 6	Menor 3
Ideal para	Múltiples acciones ante error 1	Solo registro del error 3
